# 設計判断の記録

出発点は会話で与えられた実装指示書。実装前の検証 (`research.md`) で前提が崩れた箇所を差し替えた。
**指示書からの逸脱はここに理由を書く。** 根拠が消えると後から「なぜこんな形なのか」が読めなくなる。

## ADR-0001 送信経路を画像 GET ビーコンにする

日付 2026-09-12 / 状態 採用

### 問題

指示書は UserScript から Worker へ `fetch` で POST し、離脱時は `navigator.sendBeacon` を使う前提だった。
しかし scrapbox.io の CSP は `connect-src` が allowlist で、自前ドメインが入っていない。
実機検証で `fetch` は `TypeError`、`sendBeacon` は戻り値 `true` ながら `connect-src` 違反が発火し、
どちらも送信されないことを確認した (`research.md` §1)。

指示書はこのケースを「本設計は成立しない。実装を中断し、報告すること」としていた。

### 決定

`img-src *` を使い、`new Image().src` でクエリにデータを載せた GET を Worker へ送る。
Google Analytics が長年使ってきた 1x1 GIF ビーコンと同じ仕組み。

Worker は 43 バイトの透過 GIF を 200 で返す。クライアントは `onload` で到達を判定できる
(`onload` は HTTP ステータスではなくデコード可能な画像が返ったかで決まる)。

`img.referrerPolicy = "no-referrer"` を `src` より前に設定する。既定でもクロスオリジンには
origin しか送られないが、origin も出さない。

### 帰結

- データは URL に載る。Cloudflare の上限 16KB が実効の制約。8KB を超えるなら分割送信する
- レスポンス本文を JavaScript から読めない。受信方向が必要になったら CORS 画像と canvas の
  ピクセル読み出しで実現できるが、当面は不要 (下の ADR-0003)
- `secret` が URL クエリに乗る。Cloudflare のアクセスログは Logpush を設定しない限り保存されないが、
  README に明記する。指示書 §12.1 が「secret 漏洩の実害は自分のグラフの汚染のみ」と受容しているので
  この設計と一貫する
- 画像は `keepalive` を持てないのでページ破棄時に中断される。これは ADR-0002 で無害化する

### 却下した代替案

**Cosense 自身をストレージにする。** `connect-src 'self'` なので同一オリジンへの書き込みは自由。
日次集計を自分のページの `code:kusa.json` に書き、Worker は `/api/code/...` から読む。
鍵が不要になり、複数デバイス同期とバックアップも同時に解決する。前例もある。

却下理由。Cosense 側の副作用が大きい。更新履歴が機械書き込みで埋まり、最終書き込みから 90 秒で
Slack 通知が飛ぶ。非公開プロジェクトでは Worker に Personal Access Token を預ける必要があり、
配布ツールとしては成立しない。また「できるだけ人の手を介してテキスト編集が行われるように作られている」
という Cosense の設計思想とも摩擦する。

ただし localStorage 消失対策とデバイス間同期が必要になったら、この案を後段で足せる。
書き込み手段は `@cosense/std` の WebSocket patch か、公式の `page-edit-for-ai` REST。

**Tampermonkey 前提。** `GM_xmlhttpRequest` は CSP を越えられるので指示書のまま実装できる。
却下理由は「1行書くだけで導入できる」というゴールを捨てることになる点。

**GCS への直接 PUT。** `storage.googleapis.com` が `connect-src` にある。
却下理由は署名付き URL の取得経路が自前サーバになり循環すること。公開書き込みバケットは
荒らしと課金のリスクがある。

**Sentry 経由。** `sentry.io` が `connect-src` にあり、公開 DSN は客体側に埋め込む設計なので
技術的にはデータを流せる。イベント枠の濫用であり却下。

**`media-src *` で `<video>` / `<audio>`。** request destination が `"audio"` / `"video"` になるので
Cosense の Service Worker の画像ルーティングをすり抜ける利点がある。
却下理由は Range 分割と `preload` 遅延があり画像より発火が不確実なこと。

### 2026-09-12 の改訂

2 点を差し替えた。

- **共有秘密を毎回送る方式をやめ、デバイスごとの鍵ペアによる署名にした** (ADR-0009)。
  公開提供すると決めたので、鍵が URL に乗ると運営者のログに全ユーザーの書き込み権が流れる
- **ここで却下した OAuth を採用した** (ADR-0011)。当時の却下理由は「サードパーティ Cookie が
  使えないのでどのみち localStorage に鍵が必要」「復旧は鍵を表示すれば済む」だった。
  前者は今も正しいので、OAuth はセッションではなく**身元の確定とデバイス登録にだけ使う**。
  後者は複数デバイスの自動統合という要件が加わり、かつ鍵を読まれる場所に置けないとなると
  成り立たなくなった

また、**画像リクエストの URL は Cosense の Service Worker が無条件に Cache Storage へ保存する**
(キーは URL、`Cache-Control` では止められない、48 時間で失効)。鍵を送らない設計にしたので
実害は消えたが、URL に秘密を載せない理由の 1 つとして記録しておく。

## ADR-0002 分バケットを日次ビットマップで全量送信する

日付 2026-09-12 / 状態 採用

### 問題

指示書は分バケットを1件ずつ `items` に積んで送り、`minutes` テーブルに UPSERT する。
送信成功でキューから消し、`sendBeacon` 分は成功判定できないので消さない、という設計だった。

ADR-0001 で送信が画像 GET になると、`keepalive` がないためページ破棄時に中断される。
この形だと離脱時の取りこぼしが損失になる。

### 決定

その日の分バケット集合を **1440 bit のビットマップ2枚 (write / read)** で表し、毎回まるごと送る。
180 バイト × 2 を base64url にして1日あたり約 480 文字。

サーバは受け取ったビットマップを既存のものと OR してマージし、popcount で集計値を出す。

### 帰結

4つの問題が同時に片付く。

- **マージが OR だけになり冪等性が完全になる。** 取りこぼしは損失ではなく遅延で、次回送信で復元される。
  これが画像 GET の唯一の弱点を構造的に消す
- **送信成功の判定もキュー削除も不要。** 離脱時は「早めに投げる」だけでよい
- **`minutes` テーブルが不要になる。** 書き込みは1日1行。D1 Free の日次 10 万行制限
  (2026-09-01 から強制) に対して圧倒的に軽い。指示書の設計だと1ユーザー 180 行/日だった
- **日境界をクライアントのローカル日付で決められる。** 指示書の `?tz=` で集計タイムゾーンを
  変える案は、`daily` に日付文字列で保存する設計と元から矛盾していた (過去の日の境界は動かせない)。
  タイムゾーンは表示用メタデータに留める

指示書 §5.2 の「同一の分に両方あれば write が勝つ」(`MAX(kind)`) は、サーバ側で
`r_effective = r & ~w` として実現する。`total = w + r` が二重計上なしで成立する性質は保たれる。

複数デバイスからの送信も OR でマージされるので、指示書 §4.4 の「別の端末に同じ鍵を貼る」が
正しく機能する。

### 維持した指示書の判断

「コミット数ではなくアクティブだった分のユニーク個数を指標にする」という §5.1 の核心は変えていない。
打鍵スタイルに対して不変で、集合演算なので冪等かつマージ可能、という性質がビットマップでより素直に出る。

## ADR-0003 受信方向は当面作らない

日付 2026-09-12 / 状態 採用

### 問題

指示書 §6.7 は DOM 注入版の草を `GET /v1/g/{publicId}.json` で取得する前提だった。
`fetch` が使えないので取得できない。

### 決定

DOM 注入の草は **localStorage に持つ日次集計から描く**。自分のデータは自分のブラウザにあるので、
サーバに問い合わせる必要がない。ツールチップもインタラクションも作れる。

複数デバイスを統合した草を見たいときは、共有 SVG (`<img>`) を見る。これは非インタラクティブ。

`/v1/g/{publicId}.json` はエンドポイントとして実装しておくが、UserScript からは使わない。

### 帰結

localStorage に日次集計 (53 週分の `w` / `r` / `pages` / `created`) を保持する必要がある。
371 日 × 4 値で JSON 約 15KB。localStorage の 5MB に対して問題ない。

これは ADR-0001 で却下した「Cosense をストレージにする」案への移行もしやすくする。
ローカルの日次集計をそのまま書き出せばよい。

### 将来の選択肢

受信方向が本当に必要になったら、CORS 画像と canvas のピクセル読み出しで実現できる。
`img.crossOrigin = "anonymous"` を `src` より前に設定し、Worker が `Access-Control-Allow-Origin` を
返せば canvas が tainted にならず `getImageData()` できる。CSP では `img-src` の管轄のまま通る
(effective directive は request の destination で決まるため)。

371 日 × 4 値なら 1.5KB 程度なので画像 1 枚に十分載る。

### 2026-09-12 の改訂 — 複数デバイスで穴になった

DOM 注入版は localStorage から描くので、**そのデバイスで観測した分しか持たない**。
複数デバイスを使うと「PC では PC の活動しか見えない」ことになる。

「草を見る」に 2 つの表示を置くことにした。

- **このブラウザの記録** — localStorage から描く。ツールチップ付きでインタラクティブ
- **統合された記録** — 共有 SVG を `img` で埋め込む。非インタラクティブだが全デバイス分

実装は `img` タグ 1 つで済む。受信方向を作らない判断はそのまま維持する。

なお**サインインのポップアップは例外的に双方向になる**。CSP は `postMessage` を妨げないので、
ポップアップから `window.opener.postMessage` で識別子を受け取れる (ADR-0011)。
ただしユーザー操作が必要なので、定期的なデータ取得には使えない。

## ADR-0004 バックフィルは直近 30 日に限る

日付 2026-09-12 / 状態 **ADR-0012 で置き換え**

遡る範囲を 30 日に絞ったが、そもそも実装しないことにした。
**リネームカスケードの判定方法 (`changes` の型で除外する) だけは、将来バックフィルを
作るときに再利用できるので記録として残す。**

### 問題

指示書 §11 は `/api/commits` を全ページ走査して過去 1 年分を遡る前提で、
§7.2 も「時計チェックを緩めて過去 1 年を許容」としていた。

実測すると **`/api/commits` は最終更新から約 30 日で消える** (23 日経過は残存、32 日で 0 件)。
過去 1 年の遡りは原理的に不可能。

### 決定

commits が残っている範囲だけ正確に遡る。グラフ上に「ここから計測開始」の境界を明示する。

`lines[].created` からの近似は採らない。削除・上書きされた行の履歴は失われるので常に過小評価になり、
「嘘の数字を出さない」方が誠実と判断した。

### 帰結

- 導入前の活動はほぼ残らない。指示書 §9.5 が指摘する「センサー導入前後の断絶」の対策
  (四分位スケールの母集団を `backfilled = 0` の日に限定する) はそのまま必要
- バックフィルで得た日は read が 0 なので、色相の center の母集団からも除外する

### リネームカスケード対策の差し替え

指示書 §8.3 は「同一秒に大量ページが更新されているパターンを検出して除外する」としていた。
commits の `changes` に型があるので、**`LinksChange` / `IconsChange` / `TitleChange` だけの commit を
除外する**方が確実。ヒューリスティックを使わない。

リネーム時の一括リンク更新が誰の commit になるかは未確認だが、この除外があれば帰属に関わらず安全。

## ADR-0005 配布は Cosense の公開プロジェクト経由にする

日付 2026-09-12 / 状態 採用

### 問題

指示書 §6.1 は Worker が `/v1/s.js` を配信し、ユーザーが
`import "https://kusa.example.workers.dev/v1/s.js"` の1行を書く前提だった。

Cosense は UserScript を `<script type="module" crossorigin="use-credentials">` で注入する。
credentials mode は子孫 import にも継承され、`include` では `Access-Control-Allow-Origin: *` が
拒否される。**外部ドメインからの import は成立しない。**

### 決定

バンドルを Cosense の公開プロジェクトのページに `code:script.js` として置く。
ユーザーは自分のページに1行:

```
code:script.js
 import "/api/code/<配布project>/<page>/script.js"
```

これは takker 氏が確立した慣習と同じ形で、実績がある。

### 帰結

- **開発イテレーションがむしろ軽くなる。** Cosense は `code:script.js` の SHA1 を localStorage と
  比較し、変わっていたらリロード後に手動承認を求める。ユーザー側の script.js を1行の import に
  固定しておけば、配布ページを更新しても承認は要らない
- 破壊的変更のときは配布ページを分ける。指示書 §6.1 のバージョン運用と同じ意図
- 配布ページへの反映は公式の `page-edit-for-ai` REST と Personal Access Token で自動化できる。
  当面は手動で貼る

## ADR-0006 他人の編集の除外はイベントの `by` で判定する

日付 2026-09-12 / 状態 採用

### 問題

指示書 §6.3 は `lines:changed` が他ユーザーの編集でも発火することを正しく指摘し、
「直近 3 秒以内に自分の操作がなければ他人の編集」というヒューリスティックで弾いていた。

### 決定

`scrapbox.on("lines:changed", ({by}) => ...)` の `by` を見る。
`edit` が自分のローカル編集、`remote` が他ユーザーのコミット、`navigation` がページ遷移、
`userscript` が UserScript 自身の編集。`by === "edit"` だけを write として数える。

このペイロードは 2024-10-03 のリリースノートで追加されたもので、本体の実装でも確認した。

### 帰結

ヒューリスティックが消え、誤判定がなくなる。`@cosense/types` には `{by}` の型がないので自前で宣言する。

## ADR-0007 マルチプロジェクトの扱い

日付 2026-09-12 / 状態 採用

### 問題

Cosense では 1 人が複数のプロジェクトに参加しているのが普通。
**全体を集約した草と、プロジェクトごとの草の両方**を見たい。

初期設計は `daily` の主キーに `project` を含んでいたのでデータは分けて持てたが、
運用を詰めていなかった。詰めると 4 つの判断が必要だった。

さらに**設計の穴が 1 つ見つかった**。タブを切り替えて 2 つのプロジェクトで作業した分は、
プロジェクト別のビットマップに両方 bit が立つ。プロジェクト別の `w` を単純に合計すると
同じ分を二重に数える。

### 前提として成立していたこと

**鍵はプロジェクト間で自動的に共有される。** localStorage はオリジン単位で、Cosense は
全プロジェクトが `scrapbox.io` の同一オリジン (`scrapbox.io/{project}/...`)。
プロジェクトごとに 1 行書くだけで同じ鍵が使われ、集約が成立する。
鍵の貼り付けが必要なのは Enterprise の独自ドメインを使っている場合だけ。

ただし **UserScript はプロジェクトごとに置く必要がある**。Cosense は
`/api/code/{project}/{自分のユーザー名}/script.js` しか読まないため、仕様で回避できない。

### 決定 1 — 合算は予約識別子 `*` の行で持つ

クライアントが**全プロジェクトを OR した合算ビットマップ**を `ph = '*'` として一緒に送る。

OR 済みの正しい値が永続化されるので二重計上が消える。サーバ側で計算する必要もない。
クライアントは全プロジェクトのビットマップを localStorage に持っているので OR できる。
複数デバイスでも `*` 行同士が OR されるので整合する。

代替案として「サーバ側でプロジェクト別のビットマップを OR する」も考えたが、ビットマップは
Cron で 90 日後に消えるので、それ以降は合算を再計算できなくなる。クライアントが送る方を採った。

### 決定 2 — プロジェクト識別子はハッシュにし、ラベルはオプトイン

```
ph = SHA-256(uid + ":" + プロジェクト名) の先頭 16 桁
```

**`uid` でソルトするのが要点。** ソルトなしのハッシュだと、既知のプロジェクト名の辞書で
サーバ側の値を逆引きできる。`uid` を知らなければ逆引きできない形にする。

サーバはプロジェクトを区別できるが名前を知らない。表示名は localStorage がローカルに持つ。
共有 SVG にプロジェクト名を出したいときだけ、ユーザーが設定 UI で明示的にラベルを設定して送る。

却下理由。**非公開プロジェクトの名前は Cosense 上のどこにも公開されていない情報**で、
「個人情報を持たない」という方針 (ADR 冒頭の非ゴール) に抵触する。名前をそのまま送る案は
実装が最も単純だが、この方針を崩す。完全に送らない案も検討したが、共有するときに
「どのプロジェクトの草か」が伝わらないと実用性を欠くので、オプトインに落ち着いた。

**2026-09-12 の改訂 — ラベルをサーバに置かないことにした。**
ラベルを SVG に描く設計にはエスケープの規定がなく、**SVG を直接開くとアクティブコンテンツが
実行されるので Worker オリジンでの XSS になる**。書き込み権を持つ攻撃者が被害者のラベルを
書き換え、被害者が自分の草の URL を開いた時点で発火する。

ラベルは localStorage だけで持ち、DOM 注入版の表示に使う。共有 SVG にプロジェクトを示す
文字列は出さない。貼る側が Cosense のページに見出しを書けばよい。これで `projects` テーブルと
ingest のラベル処理が消え、XSS の面もなくなる。

`ph` の長さは 12 桁から **16 桁 (64 bit)** に広げた。コストはゼロ。

### 決定 3 — publicId をプロジェクトごとに独立に導出する

```
全体用         SHA-256(uid + ":*")[0:32]
プロジェクト用  SHA-256(uid + ":" + ph)[0:32]
```

一方向なので、プロジェクト用の URL を渡しても全体の草も他のプロジェクトの草も見られない。

**2026-09-12 の改訂。** 当初は uid を秘密鍵のハッシュにしていたので、uid を知るのは本人だけだった。
ADR-0011 で uid を `HMAC-SHA256(WORKER_SECRET, "google:" + sub)` に変えたが、
**Worker 固有の秘密で HMAC するので第三者には計算できない**という性質は保たれる。
全体用の導出を `SHA-256(uid + ":*")` に揃えて、プロジェクト用と形を統一した。

却下したのは「全体用の publicId にクエリでプロジェクトを指定する」案。実装は単純だが、
**そのプロジェクトの草を共有した相手がクエリを外すだけで全体の草を見られてしまう。**
共有の単位とアクセス可能な範囲が一致しないのは設計として筋が悪い。

解決表が必要になる。

```sql
CREATE TABLE graphs (
  public_id TEXT PRIMARY KEY,
  uid       TEXT NOT NULL,
  ph        TEXT NOT NULL       -- '*' なら全体
) WITHOUT ROWID;
```

`users.public_id` はここに統合して `users` から落とす。

### 決定 4 — スケールと色相の中心は全体合算から決める

四分位スケールの母集団と色相の `center` を、常に `ph = '*'` の日次データから取る
(`backfilled = 0` に限る点は従来どおり)。プロジェクト別の草もこの共通スケールで塗る。

プロジェクト別の草を並べて比較できるのが主目的。プロジェクトごとに別のスケールにすると、
活動の少ないプロジェクトも濃く見えて比較が成立しない。

副次的に**プロジェクトの性格が色相に出る**。読むだけのプロジェクトは青寄り、書くプロジェクトは
黄寄りになる。これは意図した挙動で、並べたときに使い方の違いが読める。

`scale=self` のようなクエリは作らない。共有 URL の組み合わせと ETag のキーが増えるだけで、
比較可能性という主目的を損なう。

### 決定 5 — 記録しないプロジェクトの除外機能は作らない

**1 行書かなければ記録されない。** UserScript はプロジェクトごとに置くので、除外は導入の
有無でそのまま表現できる。設定 UI に重複した仕組みを置かない。

read 計上の on/off も全体で 1 つにする。プロジェクト単位にはしない。

### 帰結

- 活動の少ないプロジェクトの草はほぼ真っ白になる。比較可能性との引き換え
- プロジェクト名を変更すると `ph` が変わり、別プロジェクト扱いになる。Cosense の
  プロジェクト名変更は稀なので許容する。古い識別子を統合する機能は作らない
- Cron でビットマップを消した後にプロジェクト別の行だけ再送されないと、プロジェクト別の合計が
  合算を下回る。表示側でこれを矛盾として扱わない
- `ph` のバリデーションは 16 桁の 16 進数か `*` のみ許可する

## ADR-0008 作者が 1 つホストして公開提供する

日付 2026-09-12 / 状態 採用

### 問題

初期設計は運用モデルを明記していなかった。「各ユーザーが自分で Worker をデプロイする」のか
「1 つのインスタンスを公開提供する」のかで脅威モデルが変わる。

### 決定

**作者が 1 つホストして誰でも使えるように公開提供する。** 利用者は自分で何もデプロイしない。
導入は Cosense のユーザーページに 1 行書くだけ。

### 帰結

この決定が他の ADR を駆動した。

- **運営者が利用者の書き込み権を持たない形にしなければならない。** 鍵を URL に乗せると
  運営者の Cloudflare ログに全ユーザーの書き込み権が流れる。ADR-0009 で非対称鍵にした理由
- **D1 Free の日次 10 万行の書き込み上限が設計の制約になる。** 2026-09-01 から実際に強制され、
  超えると UTC 0 時まで全ユーザーが記録できなくなる。ADR-0010 で定期送信を廃止した理由
- **新規登録の乱用を抑える必要がある。** 個人用なら誰も狙わないが、公開提供では書き込み枠を
  使い切る攻撃に意味が生まれる。ADR-0011 の Google サインインがこれを構造的に抑える
- **独自ドメインが必要。** `workers.dev` では zone の WAF が効かない
- **プライバシーポリシーを置く。** Google の OAuth 同意画面の要件であり、
  「何を預けるのか」を利用者に示す責任もある

ベストエフォートであることは README に明記する。攻撃されたら招待制に切り替える。

## ADR-0009 書き込み権はデバイスごとの非対称鍵で証明する

日付 2026-09-12 / 状態 採用

### 問題

初期設計 (ADR-0001 の §4) はクライアントが生成した共有秘密を**毎回 URL に平文で送る**形だった。
公開提供すると決めた (ADR-0008) ので、これは運営者のログに全ユーザーの書き込み権が流れることを
意味する。個人用なら自分の鍵だけなので問題にならないが、公開サービスでは筋が通らない。

### 決定

**デバイスごとに ECDSA P-256 の鍵ペアを生成し、リクエストに署名する。** 秘密鍵はネットワークに出ない。

調査で実装の成立を確認した。

- ブラウザの `crypto.subtle.sign` と Workers の `verify` は**どちらも r‖s 形式** (P-256 で 64 バイト固定)。
  DER 変換は不要
- **DER を渡すと例外ではなく静かに `false` が返る。** workerd が長さをチェックして空の署名として
  扱うため。検証前に自分で 64 バイトを確認し、別のエラーとして扱う
- `importKey("raw", 65 バイトの非圧縮 SEC1, ..., ["verify"])` が使える。
  公開鍵のみ、usage は `verify` のみという制約がある

秘密鍵は **`extractable: false` で生成して IndexedDB に `CryptoKey` として保存する。**
仕様上 `CryptoKey` は structured clone の対象で、キーマテリアルを JS に露出させずに保存・再取得・
署名できる。エクスポートしないので XSS でも持ち出せない。

Ed25519 は採用しない。Workers は対応しているが、ブラウザの普及率が 88% で約 12% が未対応。
公開提供の唯一の方式にするのは早い。

### 署名対象の正規化

**`URLSearchParams.toString()` を署名対象にしてはいけない。** 空白が `+` になり、エンコード集合が
実装で違い、順序が不定で、重複キーの扱いが未定義。

固定順・固定フィールドの改行区切りにする。AWS SigV4 のような汎用の正規化は要らない。

```
署名対象 = "v=1\nu=<uid>\nd=<kid>\nt=<unix秒>\np=<p の生の値>"
```

正規化は `src/shared/sign.ts` に置いて両端で同じコードを使う。重複キーは Worker 側で 400 にする。

`t` はリプレイ窓の制限で、サーバ時刻 ±5 分を超えたら拒否する。ビットマップは OR なので
リプレイ自体は無害だが、ログから拾った URL の再送を防げる。破壊的操作は窓を 60 秒に縮める。

### 帰結

- **運営者でも他人の書き込み権を持てない。** ログに流れるのは公開鍵と署名だけ
- **デバイスを失っても鍵を失効させられる。** 他のデバイスで署名して `revoke` を送る
- 鍵が読めなくなったら (Firefox に IndexedDB の読み出し失敗の報告がある) **サインインし直して
  再登録する**。草は失われない
- 署名検証を **D1 アクセスより前に置く**。無効な署名は書き込みに触らず 403。DoS 対策として効く
- `DELETE` メソッドが使えないのは変わらない。CSP が `connect-src` を塞いでいるので、
  破壊的操作も画像ビーコンになる。署名と短いリプレイ窓、`confirm=1` の必須化で補う

## ADR-0010 定期送信を廃止して D1 Free の予算内に収める

日付 2026-09-12 / 状態 採用

### 問題

初期設計は 3 分ごとに送信して UPSERT していた。公開提供すると決めた (ADR-0008) ので、
D1 Free の日次 10 万行の書き込み上限が設計の制約になる。

サーバ側で「変化がなければ書かない」を入れても、活動が増えていればビットマップは必ず変わるので、
**書き込み回数は送信回数にほぼ比例する**。3 分ごとだと 1 人 1 日 288 行で、収容できるのは 347 人。

### 決定

**定期送信を廃止する。**

| トリガ | 動作 |
|---|---|
| ロード時 | 未送信の過去日 (前日以前) をまとめて送る。これが主経路 |
| 日付の変更を検出 | 前日分を送る。タブを閉じずに日を越えるケースのため |
| `visibilitychange` (hidden) | 当日分を送る。変化があり、かつ当日の送信回数が 4 回未満のときだけ |

| 送信頻度 | 1 人あたり 1 日 | Free 枠での収容人数 |
|---|---|---|
| 3 分ごと (当初) | 288 行 | 347 人 |
| 1 時間ごと | 54 行 | 1,851 人 |
| **採用案 (1 日最大 5 回)** | **30 行** | **3,333 人** |

これが成り立つのは**ビットマップが OR でマージされる**からで、溜めても壊れない (ADR-0002)。
そして**当日の草を自分で見るのに送信は不要**で、DOM 注入版は localStorage から描くので常に最新。
送信頻度が決めるのは共有 SVG の鮮度だけ。

### 併せて効かせること

- **インデックスを増やさない。** インデックス列を更新すると書き込みが 1 行余分にカウントされる
  (テーブル本体とインデックスで 2 行)。`graphs` に `uid` のインデックスを張らない。
  uid から引く必要があるのは削除のときだけで、`daily` の主キー前方一致で `ph` の一覧が取れる
- **UPSERT の前に SELECT し、OR した結果が既存と同一なら書かない。** 読みは日次 500 万行あるので
  余裕がある。no-op な UPDATE が rows written にカウントされるかは公式に記述がないので、
  それに依存せず明示的に分岐する
- 共有 SVG の `Cache-Control` を `max-age=900` に延ばす。送信が 1 日数回なので短くする意味がない

### 枠が尽きたとき

**500 を返す。** 画像が返らないのでクライアントは `onerror` で失敗を知り、送信済みフラグを
立てない。ビットマップは localStorage に残り翌日再送される。OR なのでデータは失われず、
反映が最大 1 日遅れるだけ。

D1 のエラーには数値コードがなくメッセージ文字列しかないので、**エラー種別に依存せず
「D1 の書き込みが throw したら 500」**にする。

### 帰結

**共有 SVG は最大 1 日遅れる。** 自分の草は常に最新なので、遅れるのは他人に見せる絵だけ。

## ADR-0011 Google サインインで身元を紐づける

日付 2026-09-12 / 状態 採用

### 問題

同じ Cosense アカウントを PC とスマホから使うのは普通。鍵はデバイスごとに生成されるので、
何もしなければ別人として記録される。要件は 3 つだった。

- **鍵を他人から読まれる場所に置かない。** 公開・非公開を問わず
- 誰でも利用でき、誰かは一意に分かる
- 複数端末のログが同一人物として統合される。全端末を失っても復旧できる

### 捨てた 4 案

**Cosense の userId をそのまま使う。** userId はページの行データに載っている**公開情報**なので、
誰でも他人を名乗れる。鍵の漏洩と違い、調べれば即座に他人の草を汚染できるので受容できない。
Cosense は OAuth プロバイダではないので、Worker が「この人は本人か」を問い合わせる先もない。

**Cosense のページに秘密鍵を置いて同期する。** そのページを読める人に書き込み権が渡る。
チームプロジェクトでは論外で、個人プロジェクトに限っても招待 URL の穴が残る
(招待 URL を知っている人は誰でも参加でき、これは API から判定できない)。
そもそも「鍵を読まれる場所に置かない」という要件に反する。

**Cosense のページに公開鍵を書き、行の `userId` で本人確認する。** 公開鍵なら読まれても害はなく、
攻撃者が他人のページに書いても行の `userId` は攻撃者自身になるので所有証明として成立する。
しかし Worker が読めるのは公開プロジェクトだけで、**識別子が公開情報から計算できてしまう**ため
活動量を非公開に保てない。共有 URL にソルトを足すと、そのソルトの同期問題が戻ってくる。

**ペアリングコード。** 何も外に出さず安全だが、**全端末を失うと復旧できない**。

### 決定

**Google サインインで身元を紐づける。** Worker は Cosense とは独立に OpenID Connect の
リライングパーティになる。

```
uid = HMAC-SHA256(WORKER_SECRET, "google:" + sub)
```

サインインは初回とデバイス追加のときだけ。日々の送信は署名で認証する (ADR-0009)。
**同じ Google アカウントでサインインすれば同じ uid になり、自動的に同じ草へ合流する。**
全端末を失っても同じなので、復旧コードは要らない。

### CSP をポップアップで回避する

**CSP は `postMessage` を妨げない。** CSP が検査するのはリソース取得、ナビゲーション、
ドキュメント設定で、`postMessage` はどれにも属さない。`window.open` も制限されない
(制限するはずだった `navigate-to` は 2022 年に仕様から削除された)。

実測した COOP も条件を満たす。scrapbox.io のプロジェクトページ (UserScript が動く場所) は
`unsafe-none`、Google のサインイン画面は **report-only** で強制されない。

フローは `design.md` の §3 にある。要点は **click ハンドラの同期的な先頭で `window.open` を呼ぶ**
こと (transient activation を失わないため、URL 構築は Worker 側でやる) と、
**state / nonce / PKCE を署名付き cookie で保持する**こと (KV の eventual consistency は
OAuth の往復時間と衝突する)。

### `sub` は Worker 固有の秘密で HMAC する

Google の `subject_types_supported` は `public` なので、**`sub` は同じ Google アカウントなら
全 OAuth クライアントで同じ値**。素の `SHA-256(sub)` を使うと、同じハッシュ関数を使う他サービスの
データと突合できるグローバル識別子になる。

`HMAC-SHA256(WORKER_SECRET, ...)` にすることで、これを防ぎつつ
**第三者が他人の識別子を計算できない**状態も作れる。捨てた案 3 の弱点がここで解消する。

`sub` そのものは保存しない。**`WORKER_SECRET` を失うと全ユーザーの uid が再計算できなくなる**ので
必ずバックアップする。

### COOP が enforced になるリスク

Google のサインイン画面の COOP は現在 report-only だが、`report-to` が設定されているのは
移行準備の典型で、**enforced に切り替わると `window.opener` が `null` になり postMessage が壊れる**。
Bluesky が 2025 年 3 月に実際に壊れた。scrapbox.io 側がプロジェクトページの COOP をルートと
揃える可能性もある (ルート `/` は既に `same-origin`)。

代替手段が乏しいので**最初からフォールバックを実装する**。ポップアップは postMessage を送った
うえで**コードも画面に表示**し、親はタイムアウト付きで待って、来なければコードの貼り付けを
案内する。**`popup.closed` のポーリングには依存しない** (COOP 下では常に `true` を返して嘘をつく)。

### Google 側の要件

- **`openid` スコープのみなら審査は不要。** 警告画面も出ず、100 ユーザー上限もかからない
  (あの上限は sensitive / restricted スコープ限定)
- 同意画面にアプリ名とロゴを出したいなら brand verification が別途必要。必須ではない
- ポリシー URL は「External + production では required」と明文があるが publish のゲートかは
  読み取れない。どちらでも用意する
- **Cosense の非 Google ログインは有料ビジネス版の申込制のみ**なので、個人利用は Google だけ。
  Google のみの対応で取りこぼしはない

### 帰結

- **新規登録の乱用が構造的に抑えられる。** 攻撃者は uid ごとに別の Google アカウントを用意する
  必要があり、鍵ペアを作るのと違って無料ではない。公開提供 (ADR-0008) でこれが一番効く
- **共有 URL が第三者に導出できない。** uid が計算不能なので
- D1 が漏洩しても Google アカウントは特定できない。`sub` を保存しないため
- ADR-0001 で OAuth を却下した判断を覆すことになる。理由の変化は ADR-0001 に追記した

## ADR-0013 運用は安い範囲に絞る

日付 2026-09-12 / 状態 採用

### 問題

公開提供すると決めた (ADR-0008) が、運用の設計が抜けていた。壊れたときに気づく手段がなく、
データの保持期間も配布の手順も未定だった。

### 決定 1 — 可観測性は Worker 側だけ

Workers Logs と Analytics Engine に集計値を出す。追加コストはほぼない。

| 指標 | 見る理由 |
|---|---|
| 日次の rows written の概算 | 枠が尽きる前に気づく |
| 署名検証の失敗率 | 鍵の不整合や攻撃の兆候 |
| ID トークン検証の失敗率と理由 | Google 側の変更 |
| **COOP フォールバックの発生率** | **Google が COOP を enforced にしたら跳ね上がる。最重要** |
| D1 のエラー率 | 枠の超過や障害 |
| 新規登録数 | 乱用の兆候 |

**uid をログに出さない。** 集計値だけにする。個別の問題を再現できなくなるが、
「サーバに個人を追跡できる記録を残さない」という方針 (ADR-0011) を運用ログでも崩さない。

**UserScript 側のエラーは送らない。** 却下理由は 3 つ。送信先が増えてリクエスト枠を使う、
何を送るのかをプライバシーポリシーに書く必要が出る、そして送らなくても
**COOP フォールバックの発生率という最重要の指標は Worker 側で取れる**。

### 決定 2 — データは削除しない (2026-09-12 改訂)

当初は「最後の送信から 2 年で消す」としたが、**数年後に振り返れることを要件として選んだ**ので
無期限保持に改めた。

| データ | 保持 |
|---|---|
| 分単位のビットマップ (`daybits`) | 90 日。重複送信をマージするための作業データで、消えても草は変わらない |
| 日次の集計値 (`daily`) | **削除しない。** 利用者が自分で削除するまで |
| 公開鍵 (`keys`) | 失効させるか、データ全体を削除するまで |

容量を見直したら無料枠で十分足りた。スキーマに無駄があったのが原因で、
**uid を 64 文字の 16 進数から 160 bit の base64url (27 文字) に短縮した**。全行に出てくるので
行サイズに直接効く。`day` と `ph` は可読性とクエリの書きやすさを優先して文字列のまま置く。

| | 値 |
|---|---|
| 1 人 1 年の容量 | 約 78KB (週 5 日稼働・3 プロジェクト) |
| Free 枠 500MB で持てる量 | 約 6,400 人年 |

1,000 人が 6 年、100 人なら 64 年。

**枠に近づいたら有料プランに移る** (月 5 ドルで 10GB)。年次アーカイブで 1 年分を 500 バイト程度の
BLOB に圧縮する手もあり、行数が 365 分の 1 になって読み取りも軽くなるが、**スキーマが複雑になるので
採らない**。容量を可観測性で監視して判断する。

利用者がデータをダウンロードする機能は作らない。共有 URL の JSON を開けば同じデータが見られる。

### 決定 3 — 配布は手動

専用の公開プロジェクトを 1 つ作り、リリースのたびにバンドルを手動で貼る。

自動化は `page-edit-for-ai` API と Personal Access Token でできるが、
**PAT はスコープがなく、そのアカウントが見られる範囲すべてにアクセスできる**。
CI の Secrets に置くリスクがリリースの手間と釣り合わない。
Service Account ならプロジェクト単位に絞れるが、ビジネスプラン限定。

リリース頻度が上がったら再検討する。

### 決定 4 — 連絡先は GitHub の Issue

プライバシーポリシーにも GitHub のリポジトリと Issue を連絡先として書く。
メールアドレスを公開せずに済み、やりとりが記録に残る。
Google の OAuth 同意画面の Homepage URL もリポジトリを指す。

### 帰結

**安さと引き換えに手間と死角が残る。** それぞれの代償は次のとおり。

- 可観測性を Worker 側だけに置いたので、**UserScript が壊れても気づけない。** 送信が来なく
  なったことは分かるが、原因がブラウザ側かどうかは切り分けられない。利用者の報告が一次情報になる
- データを削除しないので、**いつか Free 枠の 500MB に到達する。** 約 6,400 人年なので当面は
  届かないが、容量を可観測性で監視し、近づいたら有料プランへ移ることが前提になる
- 配布が手動なので、**リリースのたびに Cosense の公開プロジェクトへ貼る作業が残る。**
  破壊的変更では配布ページを分ける規約 (ADR-0005) と合わせると、貼る手間は増える方向
- 連絡先を Issue にしたので、**GitHub アカウントを持たない利用者は連絡できない。**
  無償の個人プロジェクトとして許容する

## ADR-0014 デプロイは GitHub Actions からだけ行う

日付 2026-09-12 / 状態 採用

### 問題

Cloudflare のアカウントを複数持っていて、**`wrangler login` で認証しているのとは別のアカウント**に
デプロイしたい。`wrangler login` のグローバル認証は 1 つしか持てない。

さらにローカルから手で `wrangler deploy` を打つと、どのアカウントに向いているか分からないまま
実行する事故が起きる。非対話で複数アカウントに属している場合に
**リストの先頭を黙って選ぶ挙動**が workers-sdk の issue で議論されており、未解決のまま残っている。

### 決定 1 — デプロイは GitHub Actions からだけ

`main` への push で動かす。順序は **D1 マイグレーション → コードデプロイ**。

マイグレーションを先にするのは、逆にすると新しいコードがまだ無いテーブルを引く時間帯ができるため。
**識別子はバインディング名ではなくデータベース名で指定する。** バインディング名は変わりうるが
データベース名は変わらないので、誤ったデータベースに当てる事故を避けられる (公式の注記)。

ローカルに `npm run deploy` は置かない。`npm run build` は `wrangler deploy --dry-run` なので
アカウント認証なしでバンドルの検証ができる。

### 決定 2 — ローカルは認証プロファイルをディレクトリに束縛する

wrangler 4.131.1 に認証プロファイルがある (2026-07-02 のリリースで追加)。

```sh
npx wrangler auth create <名前>
npx wrangler auth activate <名前> /Users/so/Repos/cosense-contribution-graph
npx wrangler auth list
```

ディレクトリに束縛すると、そのディレクトリ以下では自動的にそのプロファイルになる。

**ただし `wrangler auth create` / `activate` / `list` はすべて `[experimental]` と表示される。**
破壊的変更がありうるので、代替手段も用意しておく。

代替は**ワンショットの環境変数**。そのアカウント用の API トークンを用意し、必要なコマンドだけに渡す。

```sh
CLOUDFLARE_API_TOKEN=... CLOUDFLARE_ACCOUNT_ID=... npx wrangler d1 create cosense-grass
```

`wrangler login` の認証情報を壊さず、トークンをファイルに残さない。
1Password から読んで渡せば平文で置く必要もない。

### 決定 3 — ローカルに `CLOUDFLARE_API_TOKEN` を置かない

公式が優先順位を明記している。**`CLOUDFLARE_API_TOKEN` はすべての認証プロファイルを上書きする。**
シェルの rc ファイルや `.env` に置くと、意図しないアカウントに向いたまま気づかない。

`.env` に置くのは特に危うい。**wrangler CLI はこのファイルを読むが、同時にローカル開発時の
Worker の `env` にもロードされる** (`.dev.vars` も `secrets.required` も無い場合)。
ローカルの秘密値は `.dev.vars` に置き、`.env` は使わない。

### 決定 4 — `wrangler.jsonc` に `account_id` を書く

誤アカウント防止の二重化。プロファイルの束縛が外れていても、設定ファイルが対象を固定する。
アカウント ID は秘密ではないのでコミットしてよい。

**2026-09-12 の補足 — 値が揃うまではキーごと省く。** `--dry-run` は `requireAuth` を
通らないのでアカウントを一切参照せず、`wrangler types` も API を呼ばない。
**値が無いうちはキーごと省いても何も失われない** (不正な値を置くと逆に `--dry-run` が壊れる)。
段階 0 で認証プロファイルを束縛した時点で `wrangler whoami` から ID が取れたので、
同じ段階で入れた。

### 決定 5 — CI 用トークンは account-owned token にして D1 Edit を足す

**「Edit Cloudflare Workers」テンプレートに D1 は含まれない。** 公式の一覧では
Workers Routes Write / Workers Scripts Write / Workers KV Storage Write / Workers Tail Read /
Workers R2 Storage Write / Account Settings Read / User Details Read / User Memberships Read の 8 つで、
D1 がない。

**`wrangler d1 migrations apply --remote` には Account > D1 > Edit が必要。**
2025-05-02 の D1 リリースノートで、書き込みに `D1:Edit` が要ると明記された
(それ以前は `D1:Read` だけで書けてしまっていた)。

絞る方針。

- ベースは「Edit Cloudflare Workers」、**追加で Account > D1 > Edit**
- 使わない権限は落とす。KV も R2 も Tail も使っていない
- **Account Resources を対象アカウント 1 つに限定する**
- TTL (`expires_on`) を設定する。既定では期限切れしない
- **account-owned token** にする。ユーザーに紐づく token ではなく独立した権限セットなので、
  作成者のアカウント状態に左右されない

### 決定 6 — OIDC は使えないので長命トークンを Environment secrets に置く

**Cloudflare は GitHub Actions の OIDC によるトークンレス認証をサポートしていない** (2026-09-12 時点)。
`wrangler-action` の要望 (#402) と workers-sdk の議論 (#11434) はどちらも open のままで、
Cloudflare 側からの回答もロードマップの提示もない。

長命の API トークンを置くしかない。緩和策は 2 つ重ねる。決定 5 のトークン自体の絞り込みと、
**置き場を Environment secrets にすること。**

Repository secrets はリポジトリの全ワークフロー・全ジョブから読める。
Environment secrets は `environment:` を宣言したジョブだけが読み、さらに Environment 側で
**deployment branch を `main` に限定できる。** この限定は**ワークフローの `if` と独立に
GitHub 側で強制される**ので、ファイルの書き換えから独立した層になる。
段階 8 で週次の外部リンク検査ワークフローを足す予定があり、Repository secrets だと
それも射程に入ってしまう。

**required reviewers は付けない。** 毎回のデプロイが承認待ちで止まり、
「Actions から自動でデプロイする」という決定 1 と衝突する。

`CLOUDFLARE_ACCOUNT_ID` は置かない。`account_id` を設定ファイルに書いた時点で不要
(wrangler は両者を代替として扱い、設定がある方でアカウント一覧の API 呼び出しを省く)。

`cloudflare/wrangler-action` は使わず `npx wrangler deploy` を直接呼ぶ。
**マイグレーションとデプロイの順序を明示したいので、そのほうが素直。**
外部 action に依存しないという方針とも揃う。

### 帰結

- **ローカルでアカウント認証が必要なのは初回セットアップだけになる。**
  `wrangler dev` と `wrangler types` と `--dry-run` と `--local` のマイグレーションは
  認証なしで動く見込み。ただしこれは公式に明言がないので段階 0 で実測する
- トークンが漏れたら、そのアカウントの Worker を書き換えられる。
  TTL と最小権限とアカウント限定で被害の範囲と期間を絞る
- デプロイの履歴が Actions に残る。誰が何をいつデプロイしたかが後から読める
- **初回デプロイは `wrangler deploy --secrets-file` で secrets と一緒に投入する。**
  `secrets.required` を宣言していると未設定の secret があるとデプロイが失敗するため
