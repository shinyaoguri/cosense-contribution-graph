# ADR-0021 活動の内訳を 4 軸 (作る / 育てる / 関わる / 読む) で数え、草とは別の SVG で見せる

**2026-09-26、Issue #148 / #150。GitHub のプロフィールの Activity overview にならう。**

## 文脈

- 記録は「書いた分 (w)」と「読んだ分 (r)」の 2 つだけで、草もこの 2 つから描いている。草は量と読み書きの釣り合いを
  見せるが、**書いた中身の性質** (新しく作ったのか、前からあるページを育てたのか、他人のページに関わったのか) は見えない
- GitHub はコントリビューショングラフの横に、Commits / Code review / Issues / Pull requests の 4 軸のレーダーを出せる
  (research §8)。**4 軸はどれも別の行為の件数**で、図の中心からの長さは「値 ÷ 4 軸の最大値」で決まる
- 利用者はまだいない。配布済みの `v1` を使っているのは作者だけなので、**送信と保存の形を壊してよい** (持ち主が確認済み)

## 決定

### 1. 4 軸は「作る / 育てる / 関わる / 読む」で、すべて「分」で数え、軸どうしは重ならない

**書いた分 (w) を「どのページに書いたか」で 3 つに分け、読んだだけの分 (r) を 4 つ目にする。**

| 軸 | 数えるもの | 図の位置 (GitHub の軸) |
|---|---|---|
| 育てる | 自分が前に作ったページに書いた分 | 左 (Commits) |
| 作る | その日に自分が新しく作ったページに書いた分 | 下 (Pull requests) |
| 関わる | 他の人が作ったページに書いた分 | 上 (Code review) |
| 読む | 読んだだけの分 (`r & ~w`。草と同じ) | 右 (Issues) |

1 つの端末の中では 4 軸の合計が草の合計 (`w + r`) に一致する。原子単位を「分」のまま保つ (design §4)。

**最初の案 (Write / Read / Create / Link を「その行為があった日数」で数える) は捨てた。** ページの作成もリンクの作成も
必ず書くことを伴うので、Create と Link のある日は必ず Write のある日でもあり、**Write が常に最大になって
ほかの軸が Write との比でしか動かない。** GitHub の 4 軸が意味を持つのは、互いに別の行為だからで、
重ならない分け方にしないと形が情報を持たない。

### 2. 1 分のうちに種類の違うページへ書いたら、作る > 関わる > 育てる の順に 1 つへ振り分ける

タブを並べて書けば同じ分に 2 種類が立ちうる。二重に数えると 4 軸の合計が `w + r` を超えるので、1 つに寄せる。
順番は珍しい方を優先した。育てるは既定 (分類できなかった分もここに入る) で、作るは最も少ない。

### 3. 作成者と新規は、ページごとに 1 回、同一オリジンの REST で判定する

そのページで最初の `edit` (ADR-0006) が来たら、`/api/pages/v2/:project/:title` を 1 回引き、`user.id` (作成者) と
`created` (初回保存の時刻) を見る。自分の id は `/api/users/me` から取る (`scrapbox.User` に id は無い)。

| REST の結果 | 軸 |
|---|---|
| `user.id` が自分でない | 関わる |
| `user.id` が自分で、`created` がローカルの今日 | 作る |
| `user.id` が自分で、`created` がそれより前 | 育てる |

- **`user` は作成者で、`created` は最初のコミットの時刻** (research §4 の 2026-09-26 の実測)。まだ保存していないページ
  (プレースホルダー) では `user` が自分、`created` が問い合わせた時刻になるので、上の表のまま「作る」になる
- **`persistent` (保存済みか) は使わない。** 当初のプラン (#148) は「初めての `edit` のときに `persistent` が false なら新規」と
  していたが、`edit` の直後に保存が済んで true が返る競合がある。作成者と作成日で決めれば保存の前後で答えが変わらない。
  **別の端末で今日作ったページも「作る」になる** (当初のプランでは「育てる」になると書いていた)
- 結果はドキュメントの寿命の間だけ覚える。1 ページにつき 1 回しか引かない
- **判定が返るまでの分は控えておき、返ったら振り分ける。** `w` は今までどおりすぐに立てる
- **判定できなかったとき (通信の失敗など) は振り分けない。** その分は `w` にだけ入り、下の式で育てるに数えられる

### 4. 送るのは分の数だけ。育てるはサーバで引き算で出す

- 端末の中では、作る (`c`) と関わる (`o`) を `w` と同じ 1440 bit のビットマップで持つ (同じ分を二重に数えないため)
- **送るのは `c` と `o` の popcount (`wc` / `wo`) だけ。** ビットマップのまま送ると 1 エントリで 480 文字増え、
  14 エントリで URL の 8,000 文字 (design §9) を超える
- D1 は `daily.wc` / `daily.wo` に持ち、端末をまたぐときは `pages` / `created` と同じく **max で守る** (design §5)
- **育てる = max(0, w − wc − wo)。** 送らない。端末 A の「作る」と端末 B の「関わる」が同じ分に立つと `wc + wo` が `w` を超えうるので、
  0 で下を打ち切る

### 5. ビーコンを v2 にする

`/v1/p.gif` の `v=2` で、エントリに `wc` / `wo` / `links` を足す。**`v=1` は受けない (400)。**

- **区切りを URL エンコードされない文字にする。** v1 の `|` と `;` は `URLSearchParams` で `%7C` / `%3B` になり、1 文字が 3 文字になる。
  v2 はフィールドを `.` で区切り、エントリごとに `p` を繰り返す (`p` だけ重複を認める)。
  どのフィールドの文字集合 (16 進・日付の `-`・base64url の `-` `_`・数字・`*`) にも `.` は無い
- 最悪の 14 エントリで約 7,750 文字 (design §6 の見積もり)。区切りを v1 のまま 3 フィールド足すと約 7,970 文字で、余裕がほぼ無い
- パスは `/v1/` のまま変えない。`v` はこのためにある版の番号で、`/v1/` は描画と JSON を含む API 全体の版

**2026-09-26 の改訂 — 移行のあいだは `v=1` も受ける** (#151、持ち主が選んだ)。Worker が v2 だけを受けると、main へのマージで
デプロイされた時点から、配布ページ `v1` を import しているブラウザの送信が止まる。配布は `dev` で試してから `v1` に貼る順 (ADR-0005) なので、
その間も `v1` の草を育て続けるため、**v1 のエントリを `wc` / `wo` / `links` = 0 として読む。** 組み立てるのは v2 だけ。
`v1` を貼り替えた後で止める (#159)。

### 6. 草とは別の SVG `/v1/g/{publicId}/overview.svg` で見せる

- **草の SVG は 1 バイトも変えない。** 草を貼ったページの見た目も、ゴールデンテストも ETag も保たれる。
  レーダーが要らない人は貼らなければよい
- 期間は草と同じクエリ (`weeks` / `year`) で決め、その期間の 4 軸を合計する
- 描き方は GitHub に合わせる (research §8)。% は合計が 100 になる整数、長さは「値 ÷ 最大値」、0 の軸は % も頂点の円も出さず頂点を中心に置く、
  全部 0 なら四角形を描かない (十字と軸名は出す)
- **URL は草と同じ `publicId` から作る** (持ち主が選んだ)。**草の URL を受け取った人は、末尾を変えるだけで概観も見られる。**
  ADR-0020 は同じ理由で JSON を推測しにくい別の URL にしたが、概観が見せるのは**期間全体の 4 軸の割合だけ**で日ごとの値は出さず、
  草と並べて貼る使い方で URL を 2 つ渡させたくないので、ここでは分けない。利用者はまだいないので、渡し済みの草の URL について
  遡って約束を破ることにもならない。プライバシーポリシーの「共有される範囲」に書いた

### 7. 送らないもの

**ページ名・リンク先・ページ ID・作成者は送らない。** 送るのは分の数とリンクの件数だけ。

**リンクの数は軸にしない。** 書くことに含まれるので、軸にすると 1 と同じ理由で重なる。JSON に `links` (その日に作ったリンクの件数) として
載せるだけにする (Issue #155)。

## 帰結

- **一人で使うプロジェクトでは「関わる」がほぼ 0 になる。** 他人のページが無いので。形が偏るのは事実を映しているので、補正しない
- **`wc` / `wo` は複数端末で少なめに出ることがある** (max で守るため。`pages` / `created` と同じ性質、Issue #71)。その分は育てるに寄る
- **Cosense への REST が、編集したページ 1 つにつき 1 回増える。** 同一オリジンで `connect-src 'self'` を通る。`/api/users/me` はドキュメントの寿命に 1 回
- JSON (ADR-0020) に `wc` / `wo` / `links` が増える。**JSON の URL を渡した相手には、日ごとの作る・関わるの分とリンクの件数が見える** (プライバシーポリシーを改訂した)
- **草の URL を渡した相手には、期間の 4 軸の割合も見える** (決定 6)
- プレースホルダーの `scrapbox.Page.id` が保存の前後で変わらないかは、傍証だけで直接は確かめていない (research §7)。
  判定の結果をページ ID で覚えても、変わったらもう 1 回引くだけで、振り分けは変わらない
- 実装は #151 (ビーコンと D1) → #152 (センサー) / #153 (SVG) → #154 (表示) の順。リンク数は #155
