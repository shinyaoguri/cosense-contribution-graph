# ADR-0004 バックフィルは直近 30 日に限る

日付 2026-09-12 / 状態 **ADR-0012 で置き換え**

遡る範囲を 30 日に絞ったが、そもそも実装しないことにした。
**リネームカスケードの判定方法 (`changes` の型で除外する) だけは、将来バックフィルを
作るときに再利用できるので記録として残す。**

## 問題

指示書 §11 は `/api/commits` を全ページ走査して過去 1 年分を遡る前提で、
§7.2 も「時計チェックを緩めて過去 1 年を許容」としていた。

実測すると **`/api/commits` は最終更新から約 30 日で消える** (23 日経過は残存、32 日で 0 件)。
過去 1 年の遡りは原理的に不可能。

## 決定

commits が残っている範囲だけ正確に遡る。グラフ上に「ここから計測開始」の境界を明示する。

`lines[].created` からの近似は採らない。削除・上書きされた行の履歴は失われるので常に過小評価になり、
「嘘の数字を出さない」方が誠実と判断した。

## 帰結

- 導入前の活動はほぼ残らない。指示書 §9.5 が指摘する「センサー導入前後の断絶」の対策
  (四分位スケールの母集団を `backfilled = 0` の日に限定する) はそのまま必要
- バックフィルで得た日は read が 0 なので、色相の center の母集団からも除外する

## リネームカスケード対策の差し替え

指示書 §8.3 は「同一秒に大量ページが更新されているパターンを検出して除外する」としていた。
commits の `changes` に型があるので、**`LinksChange` / `IconsChange` / `TitleChange` だけの commit を
除外する**方が確実。ヒューリスティックを使わない。

リネーム時の一括リンク更新が誰の commit になるかは未確認だが、この除外があれば帰属に関わらず安全。
