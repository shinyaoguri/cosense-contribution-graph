# ADR-0023 配色を色覚に配慮した紫 ↔ 青緑 ↔ 琥珀の 1 つにする

日付 2026-09-27 / 状態 採用 / Issue #184。**ADR-0016 の決定 2・3 を置き換える** (決定 1 のスキームの差し替え口は残す)

## 問題

既定の `blue-pink` (青 → 藍 → 紫 → 赤紫 → ピンク) は、ADR-0016 決定 3 で認めていたとおり
P 型・D 型色覚に弱い。読み寄り・中間・書き寄りの 3 つを見分けられるかで測り直すと、**D 型では端と中間の色差が 0 で、
区別が付かなかった** (下の表)。色覚に配慮した `blue-yellow` は既定ではないうえ、書き寄りの濃い段が茶色に濁る
(ADR-0016 の問題)。T 型にも弱い。

持ち主と色の候補を並べて検討し、**色覚の型を問わず区別でき、ふだんの色覚でもアプリとして洗練された配色**を
既定にすることにした。検討の途中で出た持ち主の条件は次の 3 つ。

- 中間 (ふだんどおりの日) は緑がよい。厳密でなくてよいが、**順序や色の遷移があるように見えたい**
- 列は 5 つ
- 5 列が「関係ない 5 色」に見えるのはよくない。**間の列は、端と中間のあいだに見える色にする**

## 測り方

色を Machado, Oliveira & Fernandes (2009) の重さ 1.0 の行列 (P 型・D 型・T 型) にかけ、
OKLab のユークリッド距離を 100 倍した値 (ΔE) で比べる。1 マスは 10px 程度と小さいので、
5 未満だとほぼ同じ色に見える。

- **端中** … Level 2〜4、ライトとダークで、両端の列と真ん中の列の色差の最小。3 段階の読み取りを表す
- **隣** … 同じく、隣り合う列どうしの色差の最小

| 配色 | 一般 | P 型 | D 型 | T 型 |
|---|---|---|---|---|
| `violet-amber` (この ADR) | 端中 16 / 隣 8 | 9 / 3 | 12 / 3 | 12 / 4 |
| `blue-pink` (旧既定) | 7 / 4 | 2 / 0 | 0 / 2 | 6 / 4 |
| `blue-yellow` (旧) | 11 / 6 | 6 / 2 | 6 / 1 | 2 / 1 |

## 決定 1 — 紫 ↔ 青緑 ↔ 琥珀の 5 列を、表で持つ

| | 内容 |
|---|---|
| 列 (読 → 書) | 紫 / 紫みの青 / 青緑 / 黄みの緑 / 琥珀 |
| 両端と中間 | OKLCH の色相 300° / 170° / 80°。中間の彩度は端の 0.8 倍。彩度は Level 1〜4 で 0.085 / 0.11 / 0.14 / 0.16 (ガモット外は彩度を縮める) |
| 明度 | Level で決める (ライト 0.86 / 0.755 / 0.64 / 0.50、ダーク 0.34 / 0.47 / 0.60 / 0.74)。**書き寄りほど +0.05**。琥珀はもともと明るい色なので、さらに少し持ち上げる |
| 間の 2 列 | 端と中間を OKLab で半々に混ぜ、混色で落ちた彩度を半分戻す |
| 列の境界・凡例の見本・Level 0 | `blue-pink` と同じ (−0.6 / −0.2 / 0.2 / 0.6、−1 / −0.4 / 0 / 0.4 / 1、`#ebedf0` / `#161b22`) |

16 進の表は `src/worker/graph/schemes/violet-amber.ts` にある。計算して焼き込んだ値で、実行時には計算しない
(`bandScheme()`)。

選んだ理由は次のとおり。

- **明度はすでに活動量 (Level) に使っているので、読み書きは色相と彩度だけで表すしかない。**
  色相の組み合わせを総当たりで探すと、4 つの色覚すべてでの端中は 10 前後が上限だった。
  P 型・D 型で残るのは青と黄の軸、T 型で残るのは赤と緑の軸なので、両方をまたぐ組み合わせだけが上位に残る
- **中間を緑にすると、読み寄りの端は青より紫がよい。** 青を端にすると、T 型では青と緑が近く見え、
  P 型では緑も青も灰に寄って潰れる (端中 P 型 4 / T 型 5)。紫まで回すとこの衝突を避けられる。
  色相の道筋は matplotlib の viridis とほぼ同じになった
- **中間は純粋な緑 (150° 付近) まで寄せず、青緑 (170°) にとどめる。** 150° まで寄せると P 型の端中が 6 に落ちる
- **書き寄りの端は、橙より琥珀がよい。** 橙まで回すと、P 型・D 型で中間の緑と近づく (端中 6)
- **書き寄りほど明度を少し上げる。** 色相が区別できない人にも順序が伝わる手がかりになる (viridis と同じ考え方)。
  代わりに、明度が活動量と偏りの両方をわずかに表す。Level の段差 (約 0.12) の 4 割程度にとどめた
- **間の列は色相を回して作らない。** 回すと紫と青緑のあいだに鮮やかな「青」が入り、5 色がばらばらに見えた。
  OKLab で混ぜると「端と中間のあいだ」に見え、P 型の「隣」も 0 から 3 に上がる。
  単純に混ぜると灰色にくすむので、彩度を半分戻した
- **ライトの Level 1 は、Level 0 の灰と見分けられるまで下げた。** 最初の値 (琥珀 `#fff0d7`) は、
  Level 0 との色差が T 型で 3 しかなかった。下げすぎると Level 2 と詰まるので、Level 2 も少し下げた

**間の列 (2 列目と 4 列目) は、色覚の違いがある人には隣の列と同じ色に見えてよい。** 5 段階すべてを色相だけで
区別するのは無理なので、色覚を問わず保証するのは 3 段階 (端・中間・端) の読み取りにする。
間の列は、一般の色覚の人に遷移を見せるための色と割り切る。

## 決定 2 — 配色はこれ 1 つにし、`blue-pink` と `blue-yellow` を消す

持ち主の判断。色覚に配慮した配色を別に選ばせる理由が無くなり、選べる配色を残すと保守の対象だけが増える。

- **`?palette=` とスキームの差し替え口は残す** (ADR-0016 決定 1)。未知の値は既定に落ちるので、
  `palette=blue-pink` などを付けて貼った URL も壊れず、新しい配色で描かれる
- `oklch.ts` と、`CellInput` の合計分数 (`total`) は、使うのが blue-yellow だけだったので一緒に消す
- **色覚の回帰テストを足す** (`test/worker/graph/scheme-cvd.test.ts`)。登録した全スキームに対して、
  端中 ≥ 8、Level 1 と Level 0 の色差 ≥ 4.5、列の順序 (隣の列は 1 つ飛ばした列より近い) を確かめる。
  手で色を直したときに、見分けやすさが黙って落ちるのを防ぐ

## 決定 3 — アイコンの「送っている」状態は青緑にする

ページメニューのボタン・favicon・OAuth のロゴは、同じ絵 (`src/shared/grass-icon.ts`) を使う。
「送っている」状態の色を、旧既定の紫から、この配色の真ん中の列 (青緑) に替える。草らしい緑になる。

**未サインインのグレーとの色差 (4 段の最小) は、一般 8 / P 型 4 / D 型 3 / T 型 7 で、P 型・D 型では小さい** (紫の端なら 12 / 12 / 11 / 8)。
持ち主は、これを承知のうえで青緑を選んだ。

## 帰結

- **`palette` を付けずに貼った全員の草・活動の概観・ガイドの図の色が変わる。** 画像の本文が変わるので ETag も変わり、
  キャッシュは自然に入れ替わる (ADR-0015 決定 2)
- write モードの単色は青緑になる
- **合計分数で彩度を変える仕組みは、どの配色にも無くなる。** ADR-0016 の帰結に書いた
  「少ない日が書き寄りの色に見えやすい」問題 (#29) は、blue-yellow という逃げ道も無くなる
- **琥珀は明るい色なので、マスの色をそのまま文字に使うと読みにくい** (白地で Level 3 は 2.4:1)。
  ガイドの図の「書いた」「書き寄り」の文字は、同じ色相のまま暗くした `#946900` (4.9:1) にした
- OAuth の同意画面のロゴは、PNG を作り直して (`npm run logo`) Google Cloud Console で差し替える必要がある (手作業)
