# ADR-0020 日ごとの集計値を、草とは別の推測しにくい URL の JSON で出す

**2026-09-24。ADR-0013 決定 2 が「共有 URL の JSON を開けば同じデータが見られる」と前提にしていた口を、実際に作る。**

## 文脈

- 共有の草 (`/v1/g/{publicId}.svg`) が伝えるのは**四分位の Level と読み書きの色だけ**で、`daily` の `w` / `r` / `pages` / `created` を
  後から使う手段が無かった。ADR-0019 の帰結にも「当面、分数の内訳を見る手段は無い」とある
- ADR-0013 決定 2 は、ダウンロード機能を作らない理由に「共有 URL の JSON」を挙げていたが、**その JSON は初期設計の
  構成ツリー (`json.ts  GET /v1/g/{publicId}.json`) に名前が残るだけで、実装も仕様も無かった**
- SVG の中に数値を埋め込む案も検討した。Cosense の中では `<img>` なので読めず (CSP で `fetch` もできない)、
  範囲は絵のパラメータ (`weeks` / `year`) に縛られ、属性名が事実上の API になって絵の直しが破壊的変更になる。
  デモで 26KB の SVG が 15KB ほど増え、見る人の大半には要らない

## 決定

**`GET /v1/g/{publicId}/{dataKey}.json` で、その `(uid, ph)` の `daily` の全期間を返す。誰にでも渡せるが、URL は推測しにくくする。**

```
dataKey = SHA-256("data:" + uid + ":" + ph)[0:32]
```

1. **草と同じ `publicId` に `.json` を付けるだけにしない。** `publicId` は 128 bit で第三者がゼロから当てられないが、
   それだと**すでに草の URL を受け取った人が内訳を読める**。プライバシーポリシーは「内訳は本人の画面にしか表示されない」と
   約束していたので、渡し済みの URL について遡って約束を破ることになる。`dataKey` は計算に uid が要り、uid は
   `WORKER_SECRET` の HMAC なので、**草の URL からは導けない**
2. **表も状態も持たない。** Worker は `graphs` を `publicId` で引いて `(uid, ph)` を得て、`dataKey` を計算し直して定数時間で比べる。
   マイグレーションも書き込みも増えない (§11 の書き込み予算に触れない)。全削除で `graphs` が消えれば JSON も 404 になる
3. **UserScript も同じ鍵を計算できる** (uid を持っている) ので、プロジェクト別の URL は後から UserScript が出せる。
   **サーバはプロジェクト名を持たない** (ADR-0007) ので、`/account` に出せるのは合算だけ
4. `graphs` に無いのと鍵が違うのは**区別せずどちらも 404**。形が違えば D1 を引かずに 404
5. 本文は `{ total, days: [{ day, w, r, pages, created }] }`。uid も ph も出さない。**全期間を日付の昇順**で、絵のパラメータは受けない
6. ヘッダ: `access-control-allow-origin: *` (Cookie を使わない公開の値なので、ほかのサイトのスクリプトから読ませる)、
   `x-robots-tag: noindex` (公開の場に貼られても検索に拾わせない)、ETag と `Cache-Control` は草と同じ

## 帰結

- **JSON の URL を渡した相手には、日ごとの書いた分・読んだ分・編集したページ数・作ったページ数が見える。**
  プライバシーポリシーの「共有される範囲」を改訂した。草の URL が見せるものは変わらない
- `pages` / `created` は複数端末で少なく出ることがある (Issue #71)。数値は自己申告で、検証していない (design §10)
- `/v1/` を固定するので、本文の形を壊すときは `/v2/` へ上げる
- **プロジェクト別の JSON の URL はまだどこにも出していない。** UserScript のダイアログに出すのは配布ページの差し替えが絡むので別に扱う

## 2026-09-26 の改訂 — UserScript のダイアログでも出す

**草のダイアログの各囲みに、日ごとの数値の「URL をコピー」と「開く」を置いた** (#164、持ち主の要望)。合算にもプロジェクト別にも出す
(決定 3 のとおり UserScript は uid から `dataKey` を計算できる)。「渡すと日ごとの内訳まで読める。草や活動の概観の URL からは作れない」ことを
その場に添える。ダイアログは持ち主本人のブラウザにしか出ないので、決定 1 の「草の URL を受け取った人は読めない」は変わらない。
「開く」は別のタブで、Referer を送らない (`rel="noopener noreferrer"`)

## 2026-10-08 の改訂 — 時間帯を 1 日 3 分割で足す

**各日に `slots` (朝・昼・夜の書いた分と読んだだけの分) を足した** (#228、持ち主の要望)。分け方は図 (ADR-0024 決定 1) と同じ
朝 9–13 / 昼 13–18 / 夜 18–翌 9 で、夜は「D の区間 3 + D+1 の区間 0」。組み立ては図の `slotsOf` を使い回し、図と値が食い違わないようにする。

- **保存の 4 区間 (`sw0..3` / `sr0..3`) は出さない。** 暦の日で切るのは受け口の都合 (ADR-0024 決定 2) で、読み手に見せる単位は図の 3 つにそろえる
- 内訳なし (区間が NULL) の日は `slots` のキーを出さない。0 で埋めると「その時間帯に活動なし」と区別できない
- `slots` の和はその日の `w + r` と一致しない (朝は 9 時から、夜は翌朝 9 時まで)。行の無い日でも翌日の 0–9 時に分があれば、値が 0 で `slots` だけを持つ日として出す (同日の追記、#230。ADR-0024 の改訂)
- キーを足すだけなので `/v1/` のまま。プライバシーポリシーの「共有される範囲」に時間帯ごとの分を足した
